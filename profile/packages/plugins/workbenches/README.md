# QuantDSH 工作台插件平台

QuantDSH 3.0 工作台平台拥有工作台注册、管理、需求修订、开发关联和插件安装入口。工作台是具有导航、多个模块和业务数据的独立插件。简单工作台通过提示词分轮开发；复杂工作台由专业开发者离线开发后导入。两条路径沿用相同的包身份及安装规范，不使用 Puck。

## 业务包最短接入

已有平台生成的骨架时，保留 package.json 中的工作台声明和 Host 注册入口，直接实现 client.jsx 的业务页面。注册服务由宿主提供；业务包不创建注册服务实例，也不实现平台的安装器、页面外框或原生会话。

三个版本含义不同：`protocolVersion: "1.0"` 是工作台协议；`hostCompatibility.sdk: "^1.0.0"` 匹配当前业务 API 兼容版本；npm 的 `quantdsh-plugin-workbenches@3.0.0-alpha.*` 是平台实现包版本。不要把 npm 包版本填进 API 兼容字段。内核兼容值沿用本机生成的声明，不从示例猜版本。

Host 骨架已经完成以下注册，不必重新研究 Loader、registry 或服务内部实现：

```js
import manifest from './package.json';
export const inject = ['quantdshWorkbenchRegistration'];
export async function apply(ctx) {
  await ctx.get('quantdshWorkbenchRegistration').registerManaged(
    ctx, manifest.quantdsh.workbench, manifest.name + '-page');
}
```

普通 Client 只需要一个 React 页面和托管注册：

```jsx
import React, {useState} from 'react';
import {WorkbenchButton} from 'quantdsh-plugin-workbenches/client';
import manifest from './package.json';
export const inject = ['quantdshWorkbenchClientRegistration'];
function Page({workbench}) {
  const [count, setCount] = useState(0);
  // workbench.descriptor 是已核验声明；workbench.signal 在插件退出时取消。
  return <main><h1>{workbench.descriptor.title}</h1>
    <WorkbenchButton onClick={() => setCount(count + 1)}>计数 {count}</WorkbenchButton>
  </main>;
}
export async function apply(ctx) {
  await ctx.get('quantdshWorkbenchClientRegistration').registerManaged(
    ctx, manifest.quantdsh.workbench, Page);
}
```

托管业务页获得扣除平台导航后的有界内容区域；软件形态的根容器可用 `height:100%; min-height:0; display:flex; flex-direction:column`，把操作栏置于滚动列表外。不要读取浏览器窗口高度或用固定减法猜宿主布局。旧页面仍可在该区域滚动。

TypeScript 页面参数从公开 Client 入口导入 `WorkbenchPageProps`；其中只有 `workbench: {descriptor, panelKey, signal}`。`WorkbenchButton` 默认原生 `toolbar` 变体，直接使用，不必读取其实现；样式跟随宿主。

类型声明中的 `from './something.js'` 是 TypeScript 的标准 ESM 引用，同目录的 `something.d.ts` 提供类型；它不保证有同名运行时 JS。此包 Host/Client 实现已合并打包，不读取 `dist/client/*.js`、反编译 `client.browser.js` 或枚举平台私有类来推断用法。确需新能力时只核对该项官方公开契约。普通本地页面不要为未要求的业务引入存储域、跨进程通信或 Agent 工具；企业或跨账号数据另行采用已授权 Host 服务。

构建沿用骨架 `build.mjs`，Client SDK 保持 external。先用官方工作区依赖工具提供的 Node 与 pnpm JavaScript 入口安装开发工具，再执行 `node deliver.mjs`，读取开发上下文核对候选。完整启动和真实页面验收仍须完成。

## 已接入的产品代码

“用 AI 创建”允许先输入一句应用想法。Host 只准备独立的空工作区和官方 Creator 会话，需求梳理工具 `workbench_read_creation_request`、`workbench_propose_requirements` 根据实际会话归属读写候选摘要。业务面板显示可编辑摘要，后续 AI 更新不会覆盖用户正在修改的内容；旧修订必须重新核对后确认。用户确认完整需求后，沿用同一工作区和会话准备源码骨架及开发草稿。明确点击开始或确认开发后，通过原生输入提交；其他未发送草稿保留，不自动覆盖。尚未确认的想法与正式开发需求分开保存，可重新打开继续。

Host 入口 `src/index.ts` 在官方 Profile、Loader、Storage Domain、身份与权限服务上装配注册、开发、导入、启停和目录服务。Client 入口 `src/client.tsx` 使用官方 Slots/Layout 注册唯一侧栏“工作台”入口；业务工作台从列表打开，“用 AI 创建”位于管理页，并提供业务插件的 Client 注册服务。卸载时释放页面注册，当前业务页返回管理列表。

安装入口校验真实 tgz 字节、包声明、入口文件与依赖信息，保留安装归档及操作日志，通过官方插件管理执行安装或更新。启动后核对安装内容与活动模块来源，不能把上传成功或安装意图当成已生效。离线导入保留独立关联，不伪造 AI 开发需求。最终安装基线核对与包管理操作共用官方 Profile 写锁；等待锁后重新检查当前身份、宿主目标和已安装内容，基线不一致时不提交安装。

需求按修订保存，开发记录关联稳定 workbenchId、packageName、源码和原生 Session。继续调整保存新的需求修订并生成新的迭代，同一修订重试保留迭代；不创建第二个同名工作台。AI 源码候选和已有开发关联的离线上传按真实开发记录准备安装，提交及官方安装写锁内重新核对当前迭代与需求修订。陈旧候选拒绝安装，旧未知操作仍按原日志核对，不能借恢复重复安装。仅打开开发记录不发送指令；用户明确点击开始或继续开发时，通过官方会话提交接口发送本轮指令，不另建 Agent、不将模型回复视为安装回执，也不覆盖用户已有草稿。

继续开发进入时由平台重新核对当前身份、运行环境、最新需求修订、源码及原生会话关联；核对失败保留开发记录并给出对应提示，不根据旧会话中的“已完成”判断当前状态，不自动接受其他环境的目录。页面展示本轮范围和完成标准。开始或继续开发时再次核对，通过同一规范化生成器准备指令并交给原生会话提交；确认需求时留下的同一份未发送草稿可直接续交，不额外拼接前言造成自身草稿冲突。核对、提交和 AI 执行是不同事实。重试不得覆盖已有草稿、重复创建应用或扩大权限。平台服务核对不代表模型已响应，也不代表插件已安装或页面已验收。

新开发会话明确使用官方 Creator（`cordis`）预设，核对创建回执与打开后的实际预设。开发草稿显式调用官方 `cordis-plugin-development` 和 QuantDSH `quantdsh-workbench-dev` 技能，带入已保存需求、插件身份和已验证源码目录；规范正文仅维护在技能 Markdown 中。开发仍由完整原生会话、工具、模型选择及授权执行。已有开发会话不被重建或静默切换；若未使用 Creator，保留需求和源码并明确提示，不能把普通模式当作开发能力已就绪。

QuantDSH 开发技能要求先明确一件工作的业务对象、状态、用户动作、AI 分工和成果落点，再安排模块与页面。当前用户要求决定本轮交付阶段：产品定义、效果预览或开发候选；暂停打包期间不因构建成功自动继续打包安装。阶段说明是 Agent 工作要求，不是新增的 Host 状态门禁，真实操作仍沿用宿主已有授权及确认流程。

原生开发会话可调用 `workbench_read_development_context` 读取本会话关联的需求、源码和实际候选。首次原生 `plugin_manager install_bundle` 使用 `enabled:false`；随后 `workbench_verify_native_installation(version, sha256)` 核对已安装的真实字节并登记归档，用户可从候选入口核验并启用。两项工具使用官方 Agent/工具注册，不接受模型指定其他开发记录或源码路径。核验不安装、不启用，也不证明候选来自当前源码构建；安装、平台登记、活动版本和页面打开分别确认。更新旧包按官方结果重启，并核对重新注册的实际版本。

工作台内的业务加工与插件源码调整分别处理。已安装应用中的新记录、参数、核对决定和报告说明使用业务操作；界面、交互或规则实现变化才进入源码迭代。包含业务 AI 时还需验证对象绑定、真实执行、候选回流、人工加工或采用及重新打开后的状态，复制提示词或保存回执不能代替这项验收。报告编辑、候选正文读取等接口缺失时保持明确待办。

## 插件开发与集成要求

业务页的“返回工作台”由平台外框统一提供，使用原生 Layout 切换面板，不依赖浏览器历史。左侧仅保留原生“工作台”入口，不为业务应用追加平级菜单，不修改官方侧栏包。点击“工作台”进入原有管理首页，提供“已安装／我的开发”视图和应用列表。没有额外的底部切换入口或应用启动首页。用户可将最多 8 个应用设为常用，偏好存于当前本机 Profile 的原生 Storage Domain，并按组织和账号隔离；不宣称跨设备同步。既有固定偏好沿用为常用应用，不再生成侧栏一级入口。应用切换不是授权，业务操作继续检查身份与权限。当前只定位到应用入口，具体业务记录直达需另行定义稳定对象定位及访问检查。

管理首页按用户目的切换“已安装”和“我的开发”，默认突出业务使用。“我的开发”显示制作记录数量，记录和原生会话关联保留；切换视图不另建应用。已安装列表只突出名称、简短说明、状态和打开操作，版本、完整说明、启停及继续开发按需展开。导入、导入历史和刷新放在页面“更多”内，异常说明仍直接可见。管理页调整不改变原生会话、Office 和侧栏所有权。

先检查实际安装的平台类型声明、公开导出、业务包示例和内核版本，再使用对应接口。公开 Host 注册类型由包根导出；Client 服务需要平台 Client 实际加载。不得凭文档描述虚构可调用 API，不能直接读取其他插件内部存储。

工作台管理页的组件运行状态来自原生插件管理器公开的 `listBundles()` 与 `listPlugins()`，通过 bundle row 的 `entryId` 精确关联；不读取私有 Fiber，不按模块名猜测归属。加载失败、正在加载、组件活动但业务未注册和无法确认分别展示，活动组件不等于工作台页面可用。已关联开发记录的失败工作台可在工作台内继续开发，也可从管理页导入修复版本；刷新只重新核对，不执行代码修复或自动安装。安装字节核验与版本匹配的业务注册仍是独立事实。原生清单缺失、重复或版本不匹配时不宣称加载成功。此项代码检查通过不代表已安装版本或真实页面已经验收。

每个包通过 `quantdsh.workbench` 声明一个工作台，包名与描述符身份必须与开发记录一致。Host/Client 导出、Cordis 补丁和内核依赖必须满足实际安装校验。更新保留插件身份、配置与业务数据；候选试用和正式更新分开，涉及数据结构变化需要迁移与恢复验证。

项目、资料库、技能、专家和连接器由各自领域服务管理。项目关联是可选的数据归属：安装工作台不自动创建项目，多个工作台可以处理同一项目的不同业务。通过公开领域接口读取与保存成果，所有操作继续检查当前身份和权限。企业凭据留在宿主，不写入浏览器、提示词或插件包。Excel、Word 的通用打开与编辑复用系统 Office，工作台提供业务校验、分析及成果入口。

## 验证范围与未完成项

已有核心回归和官方 npm 内核隔离 Profile 的安装、启用、冷启动及质量业务链路证据。已验证另一进程持有官方写锁时，本次安装等待并在释放后核对新基线；另有两个实际包更新竞争验证：旧版 1.0.0 被另一进程更新为 1.0.1 后，排队的 1.0.2 更新因基线过期被拒绝，实际安装保持 1.0.1。测试使用无业务数据的独立包，进程崩溃、迁移及恢复仍需验收。这些证据不证明真实浏览器页面已验收。

实际浏览器管理、创建及业务页交互，Agent 生成后安装和多轮更新全流程，跨版本迁移、备份回滚、安装进程崩溃恢复，以及企业真实后端联调仍需完成。Desktop 内核安装包对齐和产品发布也须通过仓库规定的独立验收门槛。不得把构建成功称为 3.0 已交付。

从 `apps/web` 执行 `corepack pnpm --filter quantdsh-plugin-workbenches build`。在仓库根目录用受支持 Node 执行 `node --test packages/contracts/tests/workbenches.test.mjs packages/plugins/workbenches/tests/*.test.mjs`，先构建契约。实际 GUI 和企业服务联调需要另外提供运行证据。

## 公开注册类型

Host 从包根 `import type {HostWorkbenchRegistration, WorkbenchDescriptor} from "quantdsh-plugin-workbenches"`；Client 从公开入口 `import type {ClientWorkbenchRegistration} from "quantdsh-plugin-workbenches/client"`。业务插件分别取 `quantdshWorkbenchRegistration` 与 `quantdshWorkbenchClientRegistration`，使用 `registerManaged(ctx, descriptor, page)`。Host page 为页面标识，Client page 为页面组件，声明必须与安装包 manifest 一致。类型导出不提供安装权限，也不代替实际宿主授权检查。质量插件已采用公开 Client 注册类型，可作为当前集成参考。

宿主升级后，托管注册遇到已核验安装内容但内核兼容声明不匹配的旧包，会保留可释放的拒绝记录，让原生插件图继续加载；不会注册 Host 业务入口或挂载 Client 页面，也不会更改用户的插件启用选择。管理页显示“版本不兼容”，可沿原有开发记录修复后安装兼容版本。`registerManaged` 返回不代表应用已可用，仍需分别核对兼容性、实时注册和实际页面。未托管的 `register` 继续抛出兼容错误；伪造声明、安装字节变更、调用者失效及其他错误同样拒绝，不被此恢复逻辑吞掉。

## 开发源码检查点

首次源码准备生成可构建骨架，后续保持开发者文件。绑定源码前保存本机内容检查点，开发记录的 source.revision 使用 source-sha256 内容指纹。检查点存放在同一 Profile 的 quantdsh-workbench-source-checkpoints/归属目录/指纹目录；不接受页面传入目的目录。保留源码和包声明，排除 node_modules、.git、dist；单文件 16MiB、总量 64MiB、最多 2000 文件，超限或包含链接时拒绝准备并保留原源码。

“我的开发”可查看源码恢复点，并逐份点击“校验文件”。目录摘要默认未校验；校验会读取所有清单文件并核对大小及 SHA256，成功仅代表当次读取通过。关闭面板或切换记录会取消请求。公开接口只接收开发记录编号及内容指纹，源码目录由 Host 按当前身份派生。

内部恢复准备先保留当前源码检查点，再核对预期指纹、准备独立候选并复验当前源码。相同源码目录的恢复操作使用目录锁；并发请求拒绝，进程崩溃留下的锁不会自动抢占。遗留锁处理、正式文件切换和失败恢复尚未提供用户入口。该锁不约束 Agent 或外部编辑器写入。

这是开发源码恢复点，不是业务数据备份。目前尚无用户恢复入口、更新前自动恢复协议或源树整体写锁，不能据此宣布迁移/回滚完成。

## 完整原生会话与工作台外框

用户于 2026-10-17 明确授权本机 preview 的两处外框补丁，并于 2026-10-18 明确允许同一补丁用于 Desktop、验证后发布。按用户持续使用最新版并适配既有能力的要求，本轮将同样两处接缝适配到官方 `0.2.1-rc.2`，精确锁定文件版本及输入、输出 SHA256。补丁只把官方已构造的完整 Conversation 节点交给 QuantDSH 外框；页头、对话/轨迹、消息、工具、输入框、模型、权限与文件侧栏仍由官方实现。业务区居中，完整原生会话在最右侧，不添加自制会话标签栏。

这是修改官方发布文件的适配，不是未修改宿主的公共接口。Web 与 Desktop 共用 `scripts/native-workbench-frame-patch` 的同一版本和输入、输出 SHA256；未知版本或字节拒绝应用，原子替换仅改变本 Profile 的文件项，不修改其他安装的 pnpm 硬链接，并支持精确回滚。Desktop 准备阶段应用补丁，`afterPack` 再读取安装包 Resources 中的实际文件并核对输出指纹；构建检查通过仍需真实安装包的启动与页面验收，不能把底座升级仅视为版本号变更。

外框只管理自有业务页面和自有容器。原生 Conversation 节点保持一个固定 Portal 位置，收起与展开不创建第二份聊天或搬动官方 DOM。需求、安装进度与原生会话同屏；打开记录不自动发送，明确开始开发才调用既有原生提交事务。

## Agent 查询边界

QuantDSH 注册服务是本平台扩展，不属于官方预生成的 Service 接口目录；`no catalogued Service` 不能作为服务未运行的证据。官方 Config 查询的 `absent` 表示没有声明 Config Schema，不表示插件未安装。开发者应读取实际解析包的 README 和 exports 公开类型，按官方 Cordis 生命周期核对注入和注册，再做实际页面验收。完整步骤见随 QuantDSH 开发技能交付的 `references/sdk-verification.md`。

## 制作交付与用户验收

开发记录首屏根据实际安装、启用选择、Host 注册和 Client 可打开状态呈现下一步；原生工具完成、窗口重新聚焦及定时核对更新状态，不读取模型文本来判定完成。未启用显示“已安装，待启用”；运行失败或未就绪时不允许验收。安装、启用继续复用既有宿主适配，不自动重启其他任务。

用户需先打开应用并按本轮完成标准试用，主动勾选并确认后才保存验收。记录绑定组织、账号、需求修订、包名、版本、SHA256 和本机安装实例；新需求或新包不继承旧确认。Host 再次核对需求与安装注册事实后写入原生 Storage Domain。验收是用户的试用确认，不是平台自动证明所有业务场景。发现问题通过已有修改意见流程保存需求修订并沿用原生开发会话，不重新创建应用。

新接口 `/api/quantdsh-workbench-acceptance` 仅供当前账号页面读取或显式提交确认，不向模型提供自动验收工具。公开接口目录查询边界不影响该身份校验。

工作台列表与顶部“更多”复用官方 `@deepseek-ai/dsh-client-ui-primitives` 的 `Menu`，由原生渲染器共享该模块，启用 portal 定位、窗口边界约束、滚动跟随和键盘关闭；不复制官方组件。停用应用的“启用”直接显示在列表中。菜单只保留版本、常用、查看制作进度和停用等辅助操作。

## 安装前与试用检查

包检查覆盖实际归档的入口文件、声明依赖版本和可静态读取的官方工具参数。工具参数从 JavaScript 语法树读取，仅将字面量数据交给当前官方 defineTool 校验；不在正在使用的 Host 中 import 或执行候选代码。检查同时作用于平台的源码候选、离线导入、安装准备及安装提交。官方 plugin_manager 是独立安装能力；直接调用它不会自动经过平台预检，但未经平台核验的包不会因此取得工作台登记。动态定义不标为已验证。

这不是完整启动沙箱，也不证明依赖已解析安装或业务功能正确。官方包管理器仍负责实际依赖安装；原生安装、Host 活动注册、Client 页面入口和用户试用确认分别核对。启用不成功不能归为制作完成。完整隔离启动的通用执行路径仍需在官方授权和沙箱边界内实现，不在包检查中静默执行任意插件。

平台操作控件使用系统主题的背景、前景、边框及交互状态变量；中性主动作使用 toolbar 配色，不将文字前景色反用作背景。应用作者优先使用官方 Button/Input/Menu；自定义控件必须验证浅色、深色及跟随系统三种设置和两种实际颜色状态。

新建想法时，“开始梳理需求”是明确的发送动作：平台使用原生输入的 submit 事务提交开场，保留原有模型、权限、忙碌处理和失败恢复。重开已有记录仅打开会话，不自动发送。非空的其他草稿、附件或引用不覆盖；同一会话内同一开场请求不因重渲染或桥接重挂载重复提交。不确定的发送结果由原生会话处理，平台不自动重试。点击“确认需求并开始开发”后，平台先保存并核对正式需求、源码与会话关联，再通过原生输入提交开发指令；“开始本轮开发”和“保存并开始修改”也明确表示提交。打开、刷新或重新核对旧记录不会自动发送。

## 新建业务包的固定构建边界

平台生成的骨架使用项目内 `.quantdsh-pnpm-store`，避免继承全局缓存的旧权限；源码恢复点同时排除该目录与旧版 `.quantdsh-npm-cache`。构建时将 React、React DOM 与 `quantdsh-plugin-workbenches/client` 留给宿主提供，不把平台重复打入业务包。通过统一交付入口执行构建、启动检查与 pnpm 打包，不能用 macOS 系统 tar 临时拼包。安装前读取开发上下文，确认同一最终 tgz 的版本、SHA256 与兼容检查通过。检查失败保留具体错误，不能把被拒归档笼统称为候选不存在。


### 共用安装前启动检查

公开入口 `quantdsh-plugin-workbenches/startup-check` 提供 `checkWorkbenchStartup(sourceDirectory)`。仅在用户已授权的官方开发工具沙箱中执行；不要在 Host 包预览 RPC 中 import 候选代码。新工程优先执行 `node deliver.mjs`，先 build，再检查启动，失败即阻止打包；独立执行 prepack 时同样保留检查。已有工程也可执行 `node <SDK目录>/scripts/check-startup.mjs <工程目录>`，不用由 Agent 每次重写 Cordis 启动脚本。

检查在子进程中加载真实 Host 构建产物、解析声明运行依赖，使用官方 `ctx.plugin`，等待全部当前子组件生命周期，并检查依赖挂起和清理错误。15 秒超时会停止检查。子进程清空模型密钥等继承环境，使用临时 Home；临时目录与子进程不等于 OS 沙箱，执行权限仍由官方工具沙箱控制。

默认只提供工作台注册的测试适配器，并在回执中明确列出。业务包需要其他服务时，必须通过 `package.json` 的 `quantdsh.startupFixture` 指定工程内测试模块，导出 `setup(ctx,{home})`，仅加载公开实际依赖并使用临时存储及合成身份；未提供依赖的组件会失败，不会被伪造为通过。测试夹具不证明真实账号、路由、安装登记和页面可用。

回执包含包版本、实际 Host 文件 SHA256、检查范围与测试适配器。这个开发自检结果不能充当安装权限或生产启动凭证；平台继续独立核验安装字节、启用状态、Host/Client 注册和用户试用。

候选版本页面会优先核对已经安装的同版本文件。仅明确“未安装”或“安装的是另一版本”时进入安装准备；连接中断、字节不符、权限或修订冲突均停止并保留具体原因，不自动重复安装。


### 共用交付入口与耗时

新骨架执行 `node deliver.mjs`；已有工程在官方开发工具的当前权限、沙箱内执行 `<sdk.delivery.command> <sdk.delivery.runner> <source.directory>`。交付入口用 Node 运行已安装或内置的 pnpm JavaScript 文件，不依赖系统 npm、全局 pnpm 或 Windows .cmd 启动器；内置版本不匹配时明确停止。公开入口 `quantdsh-plugin-workbenches/delivery` 统一执行 build → 隔离 Host 启动检查 → pack，失败立即停止；打包关闭重复生命周期脚本，避免再次构建。候选不覆盖同名归档。报告保存于独立临时目录，逐阶段写入真实起止时间和耗时，不把日志、凭据或报告混入业务源码与归档。未完成的 running 记录视为中断、结果未确认。

开发上下文内联当前已安装版本 README 的最短接入示例、文档指纹及公共交付入口。先用示例与骨架，需要额外能力或出现实际接口错误时再查对应公开类型。这不执行 SDK，也不枚举私有实现。报告只是开发诊断；该入口的阶段报告覆盖构建、启动检查、打包；安装后状态与真实页面验收仍独立核对。


### 原生开发工具观测计时

平台通过公开 `tools/execute` 事件观测本插件已核对归属的原生开发会话，按实际 SDK 文件读取、源码文件写入、共用交付命令、原生安装及安装核对分类。原始命令、参数、输出、凭据和文件内容不进入计时记录。身份、需求修订和迭代在读写前重新核对；宿主重启后未结束的调用标为中断，不补造完成时间。诊断故障不会改变原生工具权限和返回结果。

阶段遥测仅用于测试和分析 AI 制作效率，不在工作台产品界面展示或轮询。Host 保留当前迭代的工具执行耗时、已观测工具首尾跨度和中断状态；这些记录不包含完整模型思考时间，也不是应用交付回执。没有工具事件的旧记录不补造耗时；安装发生在其他会话、手动写源码或未识别的命令时不能声称已计入。每轮最多1000条，达到上限时统计不完整。

启动检查还核对直接运行依赖与 peer 的实际安装版本，不把“模块能解析”当成满足版本范围；缺少明确 optional 的 peer 不阻断。无法按 SemVer 核对的来源明确失败，诊断不回显可能带凭据的版本 URL。这仍不等于完整传递依赖闭包证明。

业务骨架的 QuantDSH SDK peer 使用从实际已交付版本起的兼容范围（例如 `^3.0.0-alpha.48`），同时由 `hostCompatibility.sdk` 检查业务 API 契约，避免平台内部兼容修复后每个业务包都因精确锁定旧 SDK 而重新制作。官方 DSH/Cordis 依赖继续遵循目标运行时的版本约束；若确有不兼容的公开 API 变化，必须先验证适配，不能仅放宽范围掩盖错误。
