# 继续调整

先判断当前请求改变什么：已有筛选、参数、业务数据、核对决定或报告说明的加工，进入已安装工作台的业务操作；页面、交互或规则实现的调整，进入插件源码迭代；源表编辑使用系统 Office，保存新版本后明确采用。日常处理一条新记录不要求重新开发或安装插件，源码调整不重建原业务记录。用户要求先讨论产品时先梳理工作路径与影响，不提前修改源码或生成预览。

先从“我的开发”或已保存的开发记录恢复上下文，沿用关联的原生开发会话和源码。先加载官方 `cordis-plugin-development`，再读取本 Skill 的业务增量，调用 `workbench_read_development_context` 核对当前会话实际关联的完整需求、源码位置、安装目标、候选与当前版本，读取已知问题和待办；新建开发会话使用官方 Creator（`cordis`），已有会话保留历史与草稿，不静默换模式、重建会话或覆盖输入。原聊天不可用、插件未安装或已卸载，不应重建另一个插件身份。

将用户反馈写为新的需求修订，列出本轮范围和验收标准。核对源码修订、候选摘要与活动版本，写入前确认当前源码基线；并发修改先比较与合并，不能覆盖别人的修改。保持原工作台 ID、包名、业务数据和用户选定布局。

按官方 Skill 检查当前公开 API 和工具权限，在原源码上调整并验证受影响流程。安装更新遵循用户本轮授权和官方工具链，不另造安装器或手改 Profile。重新读取开发上下文核对需求基线和实际候选；候选存在不证明构建来源与当前源码一致。以实际 tgz 绝对路径为 target、`enabled:false` 调用原生 `plugin_manager install_bundle`，保留真实 `application`、`warnings`，随后以候选 version、sha256 调用 `workbench_verify_native_installation` 核对实际安装并登记。校验不再次安装、不启用或重启；旧候选不能覆盖新版本，同版本不同内容必须更正版本。已有版本更新可能需要重启，分别记录已安装、已登记、活动版本和已打开状态，不把安装成功称为页面已更新，也不自行重启无关任务。

`activationVerified:false` 仅表示该工具不核验启用，不表示启用失败，不能据此重复安装。用户已授权启用或试用时，先 `plugin_manager list_bundles`（沿 nextOffset 分页）按实际包名核对版本、error，再 `set_bundle`（target 为该包名、enabled:true），读取 application 和 nextStep。不猜 entryId、include: 前缀或以 set_plugin 代替；未获启用授权则留在工作台列表由用户操作。页面验收在当前已认证的宿主应用完成：Desktop 用运行中的 WebView，Web 用当前已登录应用页面；独立任务浏览器不自动共享宿主登录态，401 时停止该路径，不能探查/读取/复制 token、cookie、凭据或认证请求头绕过。无法操作宿主页面时保留具体“页面未验收”事实，不能以源码检查替代。

涉及数据结构时先验证迁移和恢复。恢复旧备份可能丢失新版本新增记录，不能自动覆盖；无法无损回退时保留新写入并采用向前修复。失败或结果未知时保留源码、需求及操作记录，先核对事实再恢复。

## 继续开发指令需要携带的上下文

指令引用官方 `cordis-plugin-development` 和本 Skill，补充完整需求基线、新需求与父修订、本轮反馈、现有源码目录与修订、稳定包名/工作台 ID、安装与活动版本、最近候选摘要、结果未知的操作、受影响验收及迁移约束。运行时能力以官方检查结果为准；恢复上下文来自持久记录，不能只依赖旧聊天。

执行前核对当前源码及实际库存。需求或源码已变化时先合并和重新确定本轮基线；安装结果未知时先核对，不重复安装。需求保存后开发关联失败时使用该已保存修订重试，不再次保存相同需求产生无意义版本。

调整 Office 功能继续复用系统公开能力，不复制文件编辑器。修改文件产生新修订，重新分析产生新结果，旧结果与历史报告保持原快照。AI 工具、输入版本、会话和对象绑定一起验收，切换对象或身份后旧回复不能误写；缺接口时记录具体缺口，不伪装完成。

## 局部调整工作台页面

首次提示词不要求一次完成。局部修改沿用同一插件源码，收集目标页面/区域、修改类型（样式、交互、业务规则）、描述、可选截图和明确保留范围，保存反馈与需求修订并关联当前源码基线。入口和候选预览是否可用须以当前宿主验证为准，不把文档流程当成已交付能力。

仅样式调整默认保留数据来源、接口、授权、计算规则、持久结构、其他页面和用户布局；交互调整列明受影响流程。超出本轮范围的业务规则、权限或存储变化先说明影响，再依据用户授权推进。截图辅助解释，不替代需求；源码按页面/功能组织，以便定位修改。

流程：保存修改要求与保留项 → 原源码调整 → 当前可用方式验收效果 → 在授权范围内安装与平台校验 → 核对活动版本和业务流程 → 保存迭代结果。暂停打包或安装时保留该限制；失败候选不替换已验收版本。涉及存储变更遵循迁移与恢复约束，不能承诺任意回退。

验收：仅调整分析总览时，数据接口、统计口径、历史结果和其他页面保持一致；重复修改沿用同一工作台 ID/包名；保留原生会话、草稿与业务数据；官方安装、平台登记和用户实际操作分别核实；版本冲突阻止覆盖，未验证能力明确留为待办。

核对 QuantDSH 扩展接口时遵循 [SDK 核验](sdk-verification.md)。不要把官方静态目录查询失败当成宿主缺服务，或把 Config 的 `absent` 当成未安装。

每轮修改前，先用原生 `read` 工具读取本轮将修改的已有文件；上一轮记忆、聊天里的源码或 bash/cat 输出不能代替写入工具所需的读取状态。优先对已读取文件做局部修改，避免无关整页重写；不要等生成完整大文件后才触发“先读取再写入”保护。新建文件不需要伪造已有读取记录。
