# 构建后的启动检查

构建成功只证明文件生成成功，不证明插件、工具定义和页面能够加载。交付前记录以下检查结果；缺少结果时标为未验证，不能声称应用可用。

## 工具参数

使用当前已安装版本的 `@deepseek-ai/dsh-tools` 实际执行每一个 `defineTool` 定义。当前 0.2.1-rc.2 的可选参数省略 `required`，必填参数使用 `required: true`；`required: false` 会在注册阶段抛错，使应用启动失败。不要照搬其他 JSON Schema 接口的写法；版本变化后重新核对官方声明与实际编译结果。

```js
// 可选：省略 required
weekKey: { type: 'string' }
// 必填
content: { type: 'string', required: true }
```

测试必须加载构建后的真实工具定义，不能只在测试中重写一个正确的定义。工具定义藏在插件子组件内时，单独 import 主入口不会执行这些代码。

## 优先运行平台共用检查

新工程优先执行 `node deliver.mjs`，平台统一构建、启动检查和打包，输出每个阶段的起止时间、耗时及失败原因；任一步失败即停止。上下文提供 `sdk.delivery.runner` 时，旧工程也可直接运行该平台入口，不必修改业务包。报告中的 running 阶段没有完成回执时视为中断、结果未确认，不当成通过。该报告是诊断信息，不能代替平台独立核验。兼容旧工程的 `check:startup` 与打包 prepack 仍保留；新骨架 prepack 直接调用 Node，不要求 npm。已有工程通过开发上下文 SDK 目录执行 `node <SDK目录>/scripts/check-startup.mjs <source.directory>`；必须在官方开发工具当前授权和沙箱中运行。不要为每个应用重新摸索 Cordis 生命周期或复制平台内部检查实现。

回执失败时按 `stage` 和 `errorCode` 修复。缺少服务时，用应用自己的 `quantdsh.startupFixture` 测试夹具提供公开实际依赖、临时 Storage 与合成身份；默认只有显式标记的注册测试适配器。不得为得到通过而忽略挂起的子组件。子进程和临时 Home 不是安全沙箱，仍需官方工具约束。通过只代表当前 Host 产物的隔离生命周期，不代表安装、实际注册、页面或业务验收通过。

## 插件生命周期

在隔离的临时 Home、独立 Storage 和合成身份中，通过官方 `ctx.plugin(plugin)` 加载实际构建产物，并等待完整生命周期完成；不要直接调用 `plugin.apply(ctx)` 后就宣布通过。后者可能跳过子组件依赖检查，造成“测试通过、实际启动失败”。

提供实际声明的必需依赖，确认业务服务初始化、全部工具注册、路由注册和工作台登记均发生，最后释放 Context。缺失依赖导致组件挂起也不算通过。测试不能调用付费模型、操作真实账号数据或使用真实业务目录；无法隔离的依赖明确列为尚未验证。

## 安装后的真实检查

安装字节核验、启用设置、Host 组件 active、对应版本工作台登记、Client 页面打开，是独立的检查。用户授权启用后核对所有状态，并实际完成本轮业务样例与重新打开后的数据保留检查。工具调用发生错误时保留具体错误与失败阶段，修复后重新构建新版本，不能用刷新、重启或聊天中的“已完成”替代修复。

原生安装核验回执的 `activationVerified:false` 表示工具范围之外，不能推断启用失败或重新安装。已有启用/试用授权时按回执以 `list_bundles` 核对实际包名，再 `set_bundle`，从 application 和 nextStep 判断结果；没有授权则留在工作台列表。`set_plugin` 的 entryId 只能来自真实 list_plugins，不能拿包名或猜测 include: ID 代替 bundle 选择。

页面验收使用当前已认证的宿主应用：Desktop 为正在运行的 WebView，Web 为当前已登录应用页面。独立任务浏览器不自动共享宿主登录态，401 只说明该浏览器未获访问权限；停止此路径，返回已认证宿主页面或明确记录页面未验收。不得探查/读取/复制 token、cookie、凭据文件，或附加认证请求头绕过。实际宿主入口不可用时，报告入口、错误与未验收项，静态源码检查不补作页面验收。

隔离启动检查不能代替真实页面和业务验收，也不能保证 AI 永不生成错误；它负责尽早发现可复现的启动错误。

## 平台自动包检查与运行检查

平台会在读取实际候选、上传预览、准备安装和提交安装时，自动检查归档入口、声明依赖版本以及可以从脚本语法树读取的官方工具参数。参数数据交给当前官方编译器校验，不执行上传脚本；当前已能阻止 required:false 这类错误进入工作台安装入口。动态参数和间接工具工厂不能据此声称通过。

这项检查不等于依赖安装成功或完整启动成功。实际依赖解析由官方安装器处理；完整启动检查继续使用官方工具的权限、沙箱及生命周期，随后读取真实 Host/Client 状态。没有通用隔离启动回执时，保留未验证状态，不能制造“启动检查通过”。

## 所有工作台的主题规范

应用使用宿主系统设置中的浅色、深色和跟随系统，不维护自己的颜色模式。优先从公开 SDK 导入 WorkbenchButton（默认使用原生 toolbar 样式），或使用官方 Button/Input/Menu。QuantDSH 只设默认变体，主题、键盘和焦点仍由原生控件维护。

```jsx
import { WorkbenchButton } from 'quantdsh-plugin-workbenches/client';
<WorkbenchButton onClick={save}>保存</WorkbenchButton>
<WorkbenchButton variant="outline" onClick={cancel}>取消</WorkbenchButton>
```

不要把 label-primary 当作按钮背景，也不要只绑定背景变量而把文字写死为白色。确需原生 primary 变体时，使用官方控件配对的背景和前景。自定义控件只使用当前已安装主题实际提供的变量，不编造 alias 名称。深色背景中的白色填充不必然是错误；要依据该控件的变体与前景配对核对。平台工作台的常规操作统一使用中性样式。

安装前检查不能代替界面验收。至少实际切换浅色、深色和跟随系统，检查输入框、按钮、禁用、悬浮、焦点及弹出菜单；重新打开应用后仍跟随宿主设置。只改一个示例包不能代替 SDK 和开发规范的修正。
