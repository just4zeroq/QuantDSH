# 产品要求与提交契约

本文保留产品要求与源码契约，不保存开发顺序、进度日记、部署现场或测试输出。机器索引为 [requirements.json](requirements.json)，模块索引为 [modules.json](modules.json)，有限验收见 [ACCEPTANCE](ACCEPTANCE.md)。每条要求包含源码所有者、支持入口、交付分类、数据与凭据边界、契约影响、现有检查及验收场景。

个人 Web/Desktop 与企业 Web/Desktop 使用同一个经过兼容验证的官方目标版本和相同业务插件、服务与页面。身份、执行位置与数据位置分别声明；Profile 仅选择插件和配置。官方目标版本以 package.json 的精确锁定为准，实际安装版本与 Desktop pin、alignment 和 packaged-runtime 分别核对。

企业 Web 部署在单 ECS，按账号按需启动官方进程，同账号多登录复用；运行安装共用只读基础，账号数据、配置、凭据与文件分开。Desktop 企业模式在本机执行官方 DSH，以真实成员凭据访问管理员固定后台。管理员打包配置只含 enterprise.backendUrl，不能含账号、密码或任何 Key。

企业后台独立拥有组织、成员、权限、审计与 Spring AI 内部模型 API。成员通过完整官方模型设置页手工填写内部地址、Key、协议与模型；个人模型仍可配置。普通成员不能查看他人会话，组织管理员的正文读取必须明确授权、只读并留审计；组织管理员不获得宿主运维权限。

不默认安装 SkillHub、插件广场、旧推荐目录或客户第三方市场。删除默认项不删除用户既有技能、配置、会话与显式安装记录。未来功能按 [共同开发契约](FEATURE-DEVELOPMENT-CONTRACT.md) 声明有限支持范围，不能由骨架、菜单或构建成功推导交付完成。

## 工作台复用 Office 的开发要求

工作台处理 Excel、CSV、Word、PPT 等文件时，优先使用 QuantDSH 已有 Office 插件及官方文件入口。文件预览、电子表格网格、单元格编辑、工作副本保存和支持格式的导出由 Office 拥有；工作台只实现业务字段映射、质量规则、清洗决策、统计、异常定位和报告组织，不新增独立电子表格编辑器或重复文档管理。业务指标表、异常列表与字段映射表单仍可由工作台展示。

CSV、Excel 源文件从工作台交给资料库公开入口，在官方右侧文件面板使用已有 Office 能力；工作台不另开源文件弹窗或内嵌源表网格。当前官方全屏工作台会隐藏会话右侧面板，因此打开源文件时切回真实会话，在右侧文件页提供“返回当前分析”，返回同一分析记录和业务页面。CSV 沿用只读预览，Excel 沿用已有编辑与保存能力；保存为资料库新修订后，工作台读取新版本提示，由用户明确采用并重新分析，历史结果仍引用旧版本。

开发前读取实际 Office 能力及版本，区分只读 CSV 预览、已有 XLSX 文件编辑与 Excel 工作副本接口，不能将某一路径支持的功能推定为全部支持。通过公开服务、明确资产/文档 ID 与修订关联；缺少公开接口时先在 Office 所有者中补充共享契约，并验收授权、生命周期、保存及导出，再接入工作台，不直接调用 Office 私有模块。

统计必须使用经过授权的完整数据，而不是 Office 预览的截断行列。开始分析时固定完整源文件或已保存工作副本的修订、内容摘要、工作表和区域，形成不可变分析快照；修改后重新保存并生成新运行，不改写历史结果。保留必要的后台完整解析与确定性计算，复用共享解析能力；Office 预览或编辑失败不得被当作成功导入。

验收必须覆盖：由工作台打开实际文件的 Office 入口；编辑并保存后分析使用新修订；历史运行仍引用旧快照；预览截断不影响完整统计；未授权、Office 未安装或能力不足时明确提示，不生成虚假成功或临时自制编辑器；支持的导出得到可打开的真实文件。上述场景通过前不得宣称 Office 与工作台已经打通。

## 局部调整工作台页面

首次提示词不要求一次完成。已开发工作台和未安装开发记录都支持继续修改同一插件。调整入口收集目标页面/区域、修改类型（样式、交互、业务规则）、修改描述、可选截图及明确保留范围，保存为本轮反馈和需求修订，并关联当前源码和基线版本。

仅样式调整默认保留数据来源、接口、授权、计算规则、持久结构和其他页面；交互调整列明受影响流程。Agent不能凭自由文本扩大范围，遇到必须改变业务规则、权限或存储的情况，先说明影响并由用户明确修改范围。截图辅助解释，不替代需求。页面或组件必须有稳定标识，生成模板按页面/功能组织源码，以便局部定位和修改。

流程：选择页面或区域→保存修改要求与保留项→在现有源码上开发候选→预览候选效果及改动说明→执行受影响验收→用户确认后安装更新→核对活动版本并保存迭代。候选失败或不满意不替换已验收版本，保留修改记录；涉及存储变更按迁移与恢复约束处理，不能承诺任意回退。关闭原聊天后仍可恢复此流程。

验收：仅修改分析总览的布局时，数据接口、统计口径、历史运行和其他页面保持一致；重复修改沿用同一工作台ID/包名；候选可预览、反馈可修订；更新失败不虚报成功；源版本冲突阻止覆盖。当前原型仅示意，完整局部修改、候选预览与更新链路仍待实现。

## 工作台作为多模块业务系统的要求（优先于单页原型描述）

每个工作台插件是一套可独立使用的小型业务系统，一个安装包对应一个稳定工作台身份。平台侧栏提供系统入口，打开后由插件呈现内部导航、多页面及业务流程。多个内部模块不生成多个插件，不复制或替换官方宿主、Loader、会话及平台资源管理。

首次制作必须先定义系统结构：业务目标、角色、模块清单和稳定模块ID、模块页面与导航、领域对象及关系、数据来源、操作和状态流转、Host服务及授权、可选项目关联、存储修订和迁移、模块间依赖、首轮范围及逐模块验收。页面布局是系统设计的一部分，单个页面生成不代表系统完成。

质量分析系统目标模块：分析总览；数据管理（本机/资料/企业来源及完整版本）；校验清洗（字段映射、异常和人工决策）；分析任务（分析记录、运行状态与结果）；报告中心（固定运行报告和历史）；系统配置（质量规则、资源引用和可选项目）。模块复用现有领域服务，避免每个页面独立维护另一份数据。任务执行复用既有服务与原生运行能力，不另造宿主执行器。

局部修改分为业务模块和页面组件两级。用户可在系统导航或模块树中选择业务模块，查看其页面、数据、接口和依赖，再描述调整；界面布局修改可进一步选中组件。页面属性变化通过受控配置保存；业务功能变化进入同一插件源码迭代、构建及更新。Agent必须说明跨模块影响，并对受影响数据、流程及其他模块执行回归；不得把可视化编辑器解释为业务系统生成器。

Puck、Craft.js等仅是可选界面编辑候选；目前Puck仅隔离验证组件渲染与配置文件往返，未决定产品集成，未证明任意现有代码可直接选中编辑。正式SDK及模板需先提供多模块组织、稳定定位和公开服务，再评估编辑器适配。Excel和文档编辑继续复用Office。

验收以多页面业务闭环为准：数据管理导入固定来源→校验模块保存可追溯决策→分析任务生成运行→总览读取相同运行→报告中心输出同一快照；重启后状态一致。仅修改总览样式不会改变清洗、统计和历史；更新某个业务模块能列出并验证受影响模块。当前单页原型仅作为局部交互示意，需要重新制作系统级原型，未获得用户整体确认。

## QuantDSH 3.0 候选版本边界

Desktop 与 Web 产品版本统一为 `3.0.0-alpha.2`。这是开发候选版本号，不表示已发布或已通过全部验收。实际 DSH Host、Client 和 SDK npm 包统一为 `0.2.1-rc.2`，插件包和领域 schema 使用各自版本。工具二进制归档按各平台分别锁定真实来源：Intel 仍使用官方 `rc.1` 工具归档，保留原始元数据，不携带旧 DSH npm 包，也不自动回退。Desktop 安装制品仍须核对实际 Resources 与版本、架构，未通过门禁不得发布。
